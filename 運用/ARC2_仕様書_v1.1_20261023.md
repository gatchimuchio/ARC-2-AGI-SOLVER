## 1. 目的・優先順位

**目的：既存のARC2資産で初回公式提出を実行し、実際のスコアと提出経路を確認した後、最適化と1日1回のKaggle公式提出を大会終了まで自律反復する。**

1. 既存実装・証拠・実行経路を棚卸しし、現在の再現性を確認する。
2. 既存HDS実装を原則変更せず、Kaggle実行環境への接続部分のみ最小限整備する。
3. Notebook実行と `submission.json` 生成を検証し、Kaggleへの初回提出受理・スコア取得を成立させる。
4. 初回提出時のソース、実行環境、出力、評価、失敗を保存・固定する。
5. 初回提出の**公式スコアと提出経路の確認が成立した時点で、Ownerの追加指示を待たずに性能改善へ移る**。
6. 以降、前回結果の観測→原因分析→改善→ローカル回帰試験→最良候補の選択→公式提出→新結果の保存、という閉ループを継続する。**提出はKaggle公式の上限どおり最大1日1回、稼働可能な各日で1回を目標とする**。
7. 毎日の提出は独立した履歴として保存し、次日の改善を開始する。途中の不成功・スコア低下で運転を勝手に終了しない。

目標は最終的にARC-AGI-2満点へ向かうこと。ただし「ローカル高得点」「提出ファイル生成」「Kaggle受理」「公式スコア」は別の観測結果として記録する。

## 2. 権限・保全

- 新しいOwner指示を最優先にし、`AGENTS.md`、`制御/現在状態.json`、現行指示書、実装・証拠を作業開始時に再読する。各タスクの開始時・中断再開時・状態が変わった時にも再確認する。
- 正本 `main`、証拠原本、既存HDS学習機械 `HDS/学習系統/v0.4.2`、固定された入力原本・下位モジュールを保全。破壊的操作、強制push、履歴改変、根拠のない置換は禁止。
- 初回提出までは**解法アルゴリズムを改善しない**。変更できるのは再現性の確認、提出形式への変換、実行環境への適合、提出を妨げる欠陥の最小限修理だけ。変更箇所と理由を記録する。
- 初回スコア・提出経路を確認した後の、汎用規則・HDS学習/推論/探索・候補選択の改良と日次提出は**このOwner指示により実施承認済み**。各回に追加承認を求めない。
- 既存の `制御/現在状態.json` にある `自動遷移:false` は2026-10-22時点の旧状態として観測する。今回の継続命令と衝突する場合、原因を確認した上で、新旧の履歴を保持し運用制御を最小是正する。**旧フラグを新しいOwner命令より優先して作業を止めない。**
- 課題ID・ハッシュ・索引から回答を引く方式、固定解答表、公開/非公開正解の混入、隠れ正解の探索、評価の水増しは禁止。参照用IDは追跡識別子としてのみ使用可能。
- 公開・ライセンス・外部提出の資格に関するOwner判断は代行しない。認証・大会参加が必要なら正規経路で停止して引き継ぐ。

## 5. 提出実装の入出力契約

1. KaggleがNotebookへ提供したchallengeデータから、実行時に課題集合・各課題のtest数・入力格子寸法を読み取る。120/167/172/240/259等を提出ループに固定しない。
2. 公式Notebook環境（ネットワーク無効、CPU/GPU合計12時間以内の実行制限）で必要な実装・データ・依存関係を使えるようにする。依存ファイルは大会規則に従う方法で事前添付し、実行中のGitHub/PyPI等への通信に依存しない。
3. 各入力test格子について、現行 `HDS接続` から**入力のみを根拠に**予測を取得する。既存HDSのHOLD、学習状態、推論記録を壊さない。
4. 出力は大会仕様のJSON：各課題IDに、testの個数と順序を保った配列を持ち、各要素が `attempt_1`・`attempt_2` を持つ。両候補とも適法な2次元整数格子としてシリアライズする。
5. 初回は1候補しか返さないHDSの回答を両attemptへ複製してよい。HOLDや未解決時は入力由来の中立な適法出力を明示的にフォールバックと記録し、正解・解決扱いしない。第二候補最適化は初回提出後の改良対象。
6. 型、shape、整数、色範囲、課題集合の過不足、test数、順序、JSON整合性、制限時間、ローカルとNotebook間の依存差を自動検査する。
7. `submission.json` の生成だけでは受入完了としない。実際の**Submit to Competition**の成功、提出識別情報、採点結果または審査状態を保存する。

| Gate | 成立条件 | 不成立時 |
| --- | --- | --- |
| G0 現状固定 | main SHA、作業差分、指示、アーカイブ・データの出所とハッシュを記録 | 確認不能箇所は未観測として保持 |
| G1 既存再現 | 現行ソルバを変更前条件で実行し、課題別結果・実行失敗・HOLD・所要時間を記録 | 履歴スコアを現在値として使わず原因調査 |
| G2 提出構造 | 公式challengesの全課題・全testに2候補、過不足0、型・shape・JSON検査PASS | アダプタだけ修理 |
| G3 Kaggle実行 | Internet OFFのNotebookで最初から最後まで実行し `submission.json` を生成 | 環境・結合・時間・容量を診断し最小修理 |
| G4 公式受理 | Kaggleへ提出され、提出画面に受理状態が確認できる | 未提出を記録。修理・次の可能な提出機会へ継続 |
| G5 初回スコア・経路確認 | 実際の公式scoreとNotebook→提出→採点の経路を取得・記録 | 採点待ちの間は経路・再現性を点検し、結果取得後に最適化へ移行 |
| G6 日次反復 | 提出可能な各日に原則1回、改善・ローカル試験・公式受理・score・版を記録 | 枠や採点待ちはHOLDと次回時刻を記録し、改善検討を継続 |

既存の評価分類 `E0`〜`E5` と矛盾させない。初回G5が日次最適化の開始条件となり、以降は**G6を日次繰返し**する。Kaggle公式で確認できないスコアを捏造しない。

- **日次台帳**：日付（Kaggle基準/JST）、前回公式score、仮説、変更点、ローカル成績、候補採否、提出ID、公式score、前回との差分、回帰、失敗署名、次回予定時刻。

## 8. 反復運転の契約

1. **毎日1回提出**：Kaggle ARC-AGI-2の大会固有ルールは「1日最大1提出」。残り枠と実際のリセット基準を当日のKaggle画面/APIで確認し、超過・別アカウントでの回避をしない。大会が開いている限り各提出可能日に1回を狙う。
2. **観測→改善→検査→提出→観測**：公式公開スコアを前日版と照合し、入力構造に共通する失敗、推論・学習・探索のボトルネックを特定。次の改善版を既存HDSの原理と整合する形で作り、ローカル検査後に提出する。
3. **成績の保存**：公式scoreは過去版と紐づけて保存し、良化・悪化・変化なしを全て残す。良くなかった改良は原因とともに戻せるようにし、最良既知版を消さない。
4. **毎日の独立実行**：Codexの会話継続をスケジューラとみなさず、利用可能な正規の定期実行機構と永続台帳を設ける。自動実行環境やKaggle資格情報がない場合は能力・権限の不足を具体的に報告し、可能な範囲の改善・準備・再開を継続する。
5. **提出できない日**：枠消費、審査待ち、通信/認証障害、Notebook失敗などを理由・時刻付きで記録する。解決可能な環境障害は自律修理し、次の許可された枠を確保する。
6. **停止条件**：Ownerの明示停止、Kaggle公式の最終締切・受付終了、法令/規約/認証上の権限障害など。**初回受理、初回スコア、M4報告完了は停止条件ではない。**
