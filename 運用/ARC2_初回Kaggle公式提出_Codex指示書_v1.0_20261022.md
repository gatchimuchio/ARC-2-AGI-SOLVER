4. `main` 正本・証拠・固定入力・submoduleを保全。force push、履歴の破壊、原本の改変、根拠のない設計変更を行わない。Git運用は現行 `AGENTS.md` に従う。

## D. Kaggle用の最小アダプタ（M2）

Codexは大会ルールと現行Notebook仕様を**作業時に公式ページで再確認**した上で、次を実装・検証すること。

1. Kaggle Notebookから課題JSONを読み、課題ID・test数・入力格子を実際のデータから列挙する。
2. 現行HDS解法を呼び、各test入力の予測を取得する。HDS本体は原則不変更。
3. 大会提出形式に合わせて `submission.json` を作る。各課題はtest配列、各testに `attempt_1` / `attempt_2` を必ず持つ。初回提出は同一予測の二重登録でよい。
4. HOLD／タイムアウト／例外時は原因を監査ログに記録し、入力由来の適法な2次元整数格子で補完する。補完は「解けた」と集計しない。予測の真偽を内部推測で確定しない。
5. 全task/testを列挙して、欠落0・余分0・順序維持・型/形状/値域・JSON構文を検査。120/167/172/240/259の固定件数に依存しない。
6. Kaggle上でネットワーク不要で再現できるよう、必須コード・依存データ・ライブラリを規則に適合した方法で利用可能にする。実行中の `git clone`、pip取得、API呼出しなどインターネット依存は禁止。
7. Notebookの最初から最後まで実行し、12時間以内、所定パスの出力、例外の有無、実際のJSON件数とSHAを確認する。

**変更してよい対象**：提出Notebook、入力読取・出力変換アダプタ、環境に必要な梱包、提出を阻害する明確な結合/監査器の欠陥。  
**今回変更しない対象**：探索戦略、HDS学習機械、汎用解法の設計、課題別回答ロジック、既存の正解判定基準。

**M2完了条件**：Kaggle実行環境で公式提出JSONを完走・検査PASS。ローカルのみの実行は未完了。

## E. 公式初回提出（M3）

1. Kaggleコンペへの参加・提出権限を確認。ログイン、規約同意、資格判断、ファイル公開条件でOwnerの判断が必要なら**HOLDし、依頼事項を簡潔に報告**。無断で権限を迂回しない。
2. 正規の `Submit to Competition` を実行し、提出の受理を確認する。Notebookが動いた、JSONができた、Save Versionしただけでは完了としない。
3. 受理画面・Submission ID/Version・日時・状態（Accepted/Pending/Failed等）・表示スコアを取得する。採点が未了なら「受理済・採点待ち」とする。
4. 失敗した場合は失敗原因を分類。形式ならM2へ戻り、認証・大会条件ならOwner判断を待ち、計算資源なら観測できたボトルネックの最小修理を行う。

**M3完了条件**：Kaggle公式提出記録により受理が確認できること。公式スコアの取得は評価完了後に追記する。
