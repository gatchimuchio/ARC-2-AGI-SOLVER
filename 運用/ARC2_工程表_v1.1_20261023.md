## 2. 工程間の制御

```mermaid
flowchart TD
  A["M0 現状固定"] --> B["M1 既存資産を再実行"]
  B --> C["M2 Kaggle接続と検査"]
  C --> D{ "提出形式と環境はPASS？" }
  D -->|No| C
  D -->|Yes| E["M3 公式初回提出"]
  E --> F{ "受理を確認？" }
  F -->|No| C
  F -->|Yes| G["M4 スコアと経路を確認"]
  G --> H["M5 改良・回帰検査"]
  H --> I["当日1回の公式提出"]
  I --> J{ "受付期間内？" }
  J -->|Yes 次の提出可能日| H
  J -->|No| K["M6 最終履歴の固定"]
```

- **失敗時の戻り先は原因に対応させる**。Notebook依存失敗ならM2、提出認証失敗ならOwner手続、solver例外なら再現・最小修理。無関係な全面再設計に移らない。
- 各工程・各日次サイクルの開始時に `AGENTS.md` と現行指示書、`制御/現在状態.json` を再読し、現状に合わせて判断を更新する。既存の `自動遷移:false` が新Owner指示を妨げるなら、履歴を保存して継続制御に最小是正する。
- Kaggleの公式上限は**1日1提出**。当日の残枠・時間基準・最新ルールを確認し、上限を超える操作や複数アカウントによる回避をしない。
- 終了判定は**観測された成果物**に基づき行う。ローカル120/167はKaggleの受理・公式スコアの代用品にならない。

## 3. M0・M1：既存資産の棚卸し・再現

1. `git status`、`git rev-parse HEAD`、リモート・submoduleの実態、`AGENTS.md`、指示・仕様・工程の現行版、実行環境を記録。
2. 既存の証拠アーカイブを原本から検証。候補224、120課題/167格子という履歴を出所付きで記録する。
3. `検証/ARC2評価.py` と `接続/ARC2/HDS接続.py` を使用して、実行可能な入力だけで同条件の再現試験。差があれば課題別に示す。
4. `道具/リポジトリ環境監査.py` の `戦略` 型の想定と制御状態の実態の不一致を診断。制御状態の改竄で検査成功としない。
5. Kaggle側ZIPの120課題/172格子と上流固定データの120課題/167格子を、課題・test順序で照合。**差分5格子を解答に流用しない。**

**終了成果物**：現在の正本SHA、環境、再現テスト、エラー、実測時間、入力系統別の件数表。

## 4. M2：提出用の最小構成

1. Notebook起点で、既存HDS solverを入力専用で呼び出し、内部HOLDや失敗理由を記録する。
2. 任意の課題数・test数を動的に処理し、全testの `attempt_1` と `attempt_2` を生成する。
3. JSON検証器は、格子の次元、整数値、色範囲、配列件数、キー集合、文字コード、シリアライズを検査。HOLDの合法fallbackを誤って正解扱いしない。
4. Kaggle Notebookの制約（Internet OFF、12時間上限）を満たす。外部パッケージを実行時ダウンロードしない。ローカル環境と異なる依存版・マシン資源を記録。
5. ローカルの模擬提出で検査してから、公式環境で一回通す。時間超過ならまず時間計測と既存経路の障害修理を行う。

**終了成果物**：Notebook、依存構成、アダプタ、構造検査結果、JSON SHA、実測時間、環境の差分。

## 5. M3・M4：初回提出・スコアと経路の観測

- Kaggle参加状態・権限を確認。Owner操作が必要なら期限を明示してHOLDする。
- `Submit to Competition` の操作と返却された受理・評価状態を保存。提出だけが完了したなら「スコア待ち」と明記する。
- ソースSHA・Notebook版・提出JSON SHA・入力データのハッシュ・日時を結びつけ、結果の追跡性を成立させる。
- 問題分類：環境・提出形式・予測失敗・HOLD・時間・資源・データ差異。次の性能開発の優先順位はこの分類から選ぶ。
- 初回受理後、評価Pendingなら経路・提出記録の整備を続けてスコア確定を待つ。**公式スコアと経路を観測したら即座にM5へ進む。停止・Owner再承認は不要。**

**終了成果物**：初回公式提出受理、公式スコア、提出経路、追跡可能な版の組、最初の改善仮説。

## 6. M5：日次最適化・公式提出の反復

**M4成立後に自動開始し、大会の提出受付終了まで毎日反復する。Owner承認は初回の本指示で付与済み。**

各日次サイクルの順序：

1. **観測**：前回提出の公式score・順位・評価状態・ソース版・差分とローカル実測を照合。score未公開なら「未観測」を保持。
2. **原因分析**：誤り/HOLD/実行時間/容量/候補選択を分類し、再利用可能な原因・改善仮説を定義。
3. **改良**：HDS/学習機械/探索・二候補化の必要な箇所を改修。各変更は目的・根拠・影響範囲と結びつける。
4. **検査・比較**：同条件のローカル回帰試験で、前回版・最良既知版・新候補を比較。合格候補から当日の提出物を選ぶ。
5. **1日1回の公式提出**：当日枠を確認し、制限内で提出。例外・枠消費済みなら理由と次回可能時刻を記録する。
6. **帰還・保存**：受理情報、公式score/採点待ち、Notebook版・JSON SHA・前回差・失敗署名・翌日の作業仮説を台帳へ追記。最良既知版を保全。
7. **再帰**：翌日も1へ戻る。毎日の報告・提出成功・一時的スコア悪化を停止条件にしない。

- 改良の主対象は局所的な点数操作ではなく、**どの入力条件を捉え損ね、どの推論操作・学習・探索が不成立だったか**という再利用可能な因果規則。
- 課題ID依存の回答表ではなく、入力構造・関係変換・作用・検証の汎化を対象とする。
- 評価は同一データ・同一予算・同一実行条件で「解けた数／新たに失った数／HOLD／時間」を比較。過去出力やログを置換せず、版ごとに保存。
- `attempt_2` は独立に妥当な代替仮説のある場合に活用。二案が同一でもよい。根拠なく候補を増やすことを目標にしない。
- 最終提出候補2件の選択は公式大会仕様に従い、最良既知版・直近版の比較から根拠付きで選ぶ。Ownerが最終候補の判断を指定した場合は従う。

### 継続運転の実装条件

- Codexセッションが永続実行を保証するわけではない。**利用可能な正規のスケジューラと永続的な進捗台帳を実装・設定・試運転**し、翌日も自動再開できることを確かめる。
- スケジューラ権限/資格情報が不足するときは正規のアクセス確認のみOwnerに依頼。承認不要な分析・実装・ローカル検査は継続し、状態を失わない。
- 同じ日の重複提出を禁止し、タイムゾーン差、途中失敗、再試行、先日のPendingを考慮する。**Kaggleの提出実績で日次枠を判定**し、単なるローカル予定表を信用しない。

## 7. M6：最終凍結

大会の提出受付終了を観測したら、全日次提出の履歴・最良スコア・最終選択・不成立事項を保存。受付終了後に「提出完了」と偽る行為は禁止。

## 7. 検査責任の境界

| 判定 | Codex単独で可 | Ownerが必要な場合 |
| --- | --- | --- |
| 既存資産の読取・再現試験 | 可 | 原本未提供の場合 |
| Notebook/アダプタの構築・検査 | 可 | 外部資産の利用許諾が不明な場合 |
| Kaggle大会への提出 | 正規のアクセス・参加権限がある範囲で可 | アカウント認証、初回参加、規約・公開条件の同意 |
| 性能改良の開始・日次提出 | **M4で初回score/経路確認後、自動継続** | 改善の通常判断には不要。権限・規約同意・別の外部公開判断のみ確認 |
| main履歴の破壊・証拠の改変 | 不可 | 本工程の対象外 |

## 8. 工程完了の最小報告形式

`工程 / 実行環境 / 正本SHA / 変更点 / 実測結果 / 証拠の場所 / Kaggle状態 / 未解決・HOLD / 次に必要なOwner判断`

判定語は `PASS`、`FAIL`、`HOLD`、`未観測` を区別して使う。
