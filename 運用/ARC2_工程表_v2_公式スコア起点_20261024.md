## 今回の再開位置は P1

古いM0～M3を無条件に全部やり直さない。最新リポの確認後、前回提出ID `57560705` の状態を問い合わせる。**10/23の記録は送信約1秒後の `PENDING` のみ**であり、現時点の状態ではない。

### P1：最初の実作業（最短経路）

1. `git status` / `git rev-parse HEAD`、`AGENTS.md`、`制御/現在状態.json`、既存`接続/Kaggle操作.py`、今回の3文書、日次台帳を確認。
2. 正規のKaggle認証が設定済みなら、**読み取り専用**の既存コマンド `python 接続/Kaggle操作.py 履歴` を実行。実装と引数を確認した上で使用する。Windows実環境を優先する。
3. 公式提出ID `57560705`、競技 `arc-prize-2026-arc-agi-2`、実際のstatus、`public_score`、失敗説明の有無、UTC取得時刻を保存。対象が直近20件から消えた場合は履歴を広げ、別IDの値で代用しない。
4. `public_score` が `0` や `0.00` なら**有効なゼロ点**。空欄・nullなら**未観測**。
5. 数値があれば**直ちにP4→P5**。`PENDING`ならP2。終了しても空欄・エラーならP3。認証不可は停止原因と必要な最小操作を明記。

### P2：1秒観測で終えないための継続契約

- `PENDING` 後、約5分→15分→30分→約1時間間隔で同一IDを観測し、その後も持続的に追跡する。照会間隔はKaggle応答・実環境に応じ安全な範囲で調整してよい。
- 毎回、`観測日時 / status / score / error / 次の観測時刻 / 採点対象ID`を追記。**監視開始の成功ではなく、監視の再起動試験をPASS条件とする**。
- 数時間の遅延やキューを勝手に採点失敗と断定しない。24時間超の未確定は障害調査項目に追加し、大会の既知障害・Notebook版・出力・アカウント状態を確認する。**監視は継続**。
- Codex対話終了に備え、既存の正規環境で持続する定期ジョブを作成し、模擬PENDING→模擬数値scoreの遷移と、実IDの安全な再照会を検証する。資格情報・操作権限が不足する場合は不足点を報告し、設置成功と偽らない。

### P3：異常時の原因別帰還

| 観測障害 | 処理 | 禁止 |
| --- | --- | --- |
| `COMPLETE`だがscoreなし | 提出failure description、Kaggle競技判定、Notebookの実行/出力、JSONの対応を照合 | 空欄を0と記録、再実行前の原因放置 |
| Notebook未完・失敗 | 実際の該当版・実行ログ・依存・時間・メモリを確認し最小修理 | 前回と異なるNotebook版の結果を転用 |
| 公式sampleとの不一致 | 公式testのtask/test数・順序・2候補構造を再照合 | `evaluation`120/172を`test`240/259として提出 |
| Kaggle側Pending長期化 | 公式履歴・サービス情報・大会discussion/案内を再観測し、同一IDを追跡 | 根拠なく失敗断定、枠を無駄にする二重提出 |
| 認証・権限・規則未成立 | 保存済み正規資格情報と参加状態を確認。不足権限はOwnerへ最小限の質問 | 認証情報をログ・リポへ転記、勝手なアカウント作成 |

**修復の対象は採点経路。P4成立前にHDS学習/探索/解法の全面最適化へ逸脱しない。**

1. `PENDING`記録後にCodexを終了・再起動した想定でも**同一IDを再照会**する。

8. GitHub `main`と旧証拠・`AGENTS.md`の保持契約を守り、新運用の記録は追記・別版として残す。
