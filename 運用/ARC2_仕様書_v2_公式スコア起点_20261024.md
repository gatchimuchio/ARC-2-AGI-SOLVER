## 0. 最上位目的と成立条件

**現行リポ資産で公式提出を成立させ、その提出の公式数値スコアと提出経路を取得・保存する。それを基準に学習・最適化し、公式結果で検証する1日1回の提出を大会の受付終了まで反復する。**

優先順位は `公式結果の取得 > 採点経路の修理 > 実測に基づく学習・最適化 > 日次再提出`。**公式スコアが未取得の間、スコア向上を目的とした解法改変・性能改善の採用を開始しない。** ただし結果取得、通信・形式・採点経路の診断と修復、およびそれらの確認試験は実施する。

公式スコアは外部目的との照合基準。ローカルの正答率、train-exact、HOLD減少、Notebook完走、提出受理は必要な補助観測であって、公式スコアの代用ではない。**スコア `0` は観測値、空文字・null・未取得は未観測**。公式スコアは集計指標であり、個々の規則の正しさを単独で証明しないため、同条件のローカル証拠との対応を監査する。

## 2. 公式スコア成立契約【必須ゲート G-SCORE】

`G-SCORE=PASS` と判定できるのは**同じ公式提出**について、次をすべて取得できた場合だけ。

1. Kaggle認証済みの `arc-prize-2026-arc-agi-2` 提出履歴に対象submission IDが存在する。
2. 対象submission IDの採点が完了し、**公式の数値 `public_score`（ゼロを含む）**が取得できる。空欄・推定・別版の値は不可。
3. 対象ID ↔ Notebook所有者/slug・version ↔ ソースcommit ↔ 提出JSON SHA-256 ↔ 使用データ ↔ 実行日時が追跡できる。
4. スコアを取得した正確な観測日時（UTC/JST）、取得経路、API/画面の実測結果を保存する。

状態は以下を混同しない。

| 状態 | 意味・次の動作 |
| --- | --- |
| `PENDING` / 実行待ち | 採点未確定。**同一IDを継続監視**。再提出しない |
| `COMPLETE` ＋ 数値スコア | `G-SCORE=PASS`。経路を固定して最適化に進む |
| `COMPLETE` ＋ 空スコア | **異常・未成立**。`error_description`、競技設定、Notebook再実行、提出形式・入力を調査。`0` と誤読しない |
| `FAILED` / format error / Notebook error | **採点失敗**。原因を現物で確認、経路の最小修理。次の正規提出可能日を確認して再試行 |
| 認証・通信障害 / 該当ID不明 | **観測不能**。口座・大会・アクセス・履歴を確認。確認不能のまま成功宣言も再送も不可 |

監視実装は一度の確認で終わらせない。既存 `接続/Kaggle操作.py 履歴` による公式照会を起点とし、即時、約5分、約15分、約30分、その後おおむね1時間ごと等、負荷を抑えた再照会間隔を採用する。**照会時刻・結果をその都度追記**し、Codexセッション終了時も正規の再開機構へ引き継ぐ。時間経過を `FAILED` と決めつけない。長時間未採点なら最新の大会障害情報・Notebook状態を調べ、24時間を超えたら障害として報告・再診断し、監視は継続する。期限による不成立をスコア取得済みに書き換えない。

## 3. Kaggle提出契約と保全条件

- 対象大会と公式 `sample_submission.json` を照合し、`arc-agi_test_challenges.json` の全task ID・全test数・順序・2候補構造・格子値域を検査。評価用 `arc-agi_evaluation_challenges.json` と取り違えない。240/259は過去の実測であり件数固定条件ではない。
- Kaggleで実行済みのNotebook版と実際に提出した版が一致すること。Notebook `COMPLETE` やJSON生成だけでは「採点成立」と呼ばない。
- HOLD等のfallbackは適法な形式でも**解いた数・正答数に算入しない**。2候補が同じなら独立した正解2件と集計しない。
- 入力・teacher・評価正解・hidden情報の隔離、課題ID/hashに紐づく答え分岐禁止、現行HDS/学習機械基底の保護は `AGENTS.md` に従う。
- Kaggleアカウント/認証情報は正規設定を利用。トークンやcookiesを文書・GitHub・ログへ保存しない。利用権限がない場合は権限を迂回しない。
- 公式大会規則は**最大1提出/日、最終候補最大2件**。日付境界・枠残・締切は作業当日のKaggle公式値で再確認する。2026-10-26 23:59 UTC参加締切、11-02 23:59 UTC最終提出締切は2026-10-24時点の参考値。

## 4. スコア取得後の閉ループ契約

`G-SCORE=PASS` 後に限り、次を繰り返す。

1. **前回公式結果を観測・固定**：score、提出ID、版、時刻、成否。ローカル実測と同じ変更単位で対応づける。
2. **失敗機構の特定**：まず258/259 HOLDの内訳（理由、機構の採否、制約、実行時間、出力競合）を個別ログで調べ、入力条件→規則→出力の失敗を分類する。
3. **改善仮説の実装**：汎用的なHDS学習・推論・探索・2候補の改善。答えの記憶・ID別対処は禁止。
4. **同条件ローカル比較**：前回版・最良版・新候補について正答数／HOLD／失敗／時間／退行を実測。検証が未成立なら改良版を採用しない。
5. **当日の公式提出**：上限と前回採点の成立を確認し、各提出可能日に1回を運用目標として、検証済みの候補を送信。曖昧な送信応答で再送しない。
6. **同じIDの公式採点を回収**：`G-SCORE` と同じ厳格さで回収し、前回・最良scoreと差分を固定して翌日の判断へ帰還する。**新スコア未取得を改善成功と報告しない**。

提出後の `PENDING` が翌日まで続き、前回の公式結果が未取得なら、**根拠不明の次提出を強行せず採点経路修理を優先**する。この場合「予定した日次提出が成立しなかった障害」として記録し、黙って成功扱いしない。対象スコアが得られたら速やかに通常ループへ戻る。

## 5. 継続実行・停止条件

作業者の単一Codexセッションを永続実行基盤とみなさない。Windows-firstの実環境で利用可能な**持続するスケジューラ＋Kaggleの状態取得処理＋Codexが実際に再開できる実行経路**を選定・設置・試験する。スケジューラだけが時刻を知らせても、自動最適化が起動しなければ日次自動化は**FAIL**。GitHub Actions未実行をCodex稼働の証拠にしない。認証を無断共有・複製しない。

チェックポイントは履歴追記型。最低限 `phase, last_submission_ref, last_status, official_score, observed_at_utc, last_submitted_utc_day, next_check_at_utc, source_sha, notebook_id/version, submission_sha256, blockers, next_action` を保持する。再起動後に**まず公式履歴を再取得**し、同一日の二重提出を防ぐ。`AGENTS.md` と保護対象の `制御/現在状態.json` をこの文書だけで無断変更しない。新運用状態は別ファイルに記録し、旧状態との齟齬を明示する。

運用完了は大会の公式受付終了と証拠・最終候補の固定を確認したとき。Owner明示停止、実際の権限・規約障害などは正確に報告するが、**`PENDING`、日報作成、スコア取得、単一日の提出を最終終了条件としない**。

## 6. 受入基準

| Gate | PASSの必要証拠 |
| --- | --- |
| G0 現状観測 | 最新SHA・指示・現行IDの照会結果・未観測項目が記録される |
| G1 採点経路 | 出力・Notebook・submission IDの対応が追跡可能。失敗なら生成箇所まで原因を特定 |
| **G2 公式スコア** | **同一submission IDに公式数値score（0含む）＋取得時刻＋経路が保存される** |
| G3 継続運転 | セッション切断・再起動・日付境界の模擬試験で監視と次工程が実際に再開する。二重送信なし |
| G4 最適化 | **G2後**、同条件比較・差分採否・公式次スコアを保存する |
| G5 日次反復 | 提出可能な各日について試行と結果／不能原因・次回再開時刻が保持され、翌日も継続する |

**G2未成立ではG4・G5をPASSとしない。HOLDを成功に読み替えない。**
