## 0．工程の絶対順位

**再現性の回復と実証 → 競技能力の接続 → 得点観測 → 得点の改善。**

ARC2・ARC3は目的と検査原理を共有するが、ゲーム操作と格子推論は混線させない。各リポジトリに独立の履歴・指示単位・学習記憶・スコア台帳を置く。1作業単位ごとに実装／証拠／合否／次作業を閉じ、改修前の状態へ戻せるようにする。

### 開始時点の事実（2026-10-25の監査）

- ARC2：現行mainの提出用実装は259出力のうち258件が保留由来fallback。事前記憶の主要部はbundleに含まれない。二候補は複写。公式画面で直近0.00、歴代に0.83という表示があるが、対応ソースの同定が必要。
- ARC3：現行mainの提出agentはRESET／HOLD中心の非攻略基線。事前記憶はbundleから除外。公式画面で23.86／0.03等の得点履歴があるが、Notebookごとのコード同一性は未確認。
- ARC2：既存の局所120課題／167格子実績。ARC3：公開サンプルでのレベル到達実績。いずれも現在の本番スコアを保証しない。
- 旧工程表は「形式の正常性」や「初回提出」が先行した。今回、過去資産の再現と得点への作用確認を工程の前段へ移す。

| P1 得点版の身元特定 | 両方 | Kaggle提出履歴とNotebook実体、ソース・bundle・scoreを対応付け | 0.83／23.86等の版同一性が「確認済み／未観測」に分類済み | P1継続。未回収値を現行版へ帰属しない |

**Gate管理の注意：** P2の歴代Notebook・依存環境を取得できない場合は「歴史的成果は再現未確認」と明示し、無期限に停止しない。P3でゼロから現行の**新たな再現可能基準線**を確立し、P4以降へ進む。ただし「過去0.83／23.86を再現した」とは言わない。P3〜P6の競技能力の検査は省略不可。

## 2．P0／P1：過去成果を失わず、得点版の身元を確定

### ARC2

1. 120課題・167格子の局所成果の元コミット、使用データ、評価器、メモリ状態を探す。過去Gitブランチ、報告書、GitHub Actions、保存実行物を確認する。
2. 2026-10-23公式提出ID 57560705の最終statusと表示scoreを再取得する。過去画面の0.00と同じ提出か照合する。
3. Kaggle上の歴代0.83についてNotebook ID／version／提出ID／ソース一式を探す。見つからなければ「出典は画面表示のみ」として数値だけ保全する。
4. 学習・テスト混入のない当時の評価条件を復元し、元の成功と今の0.00を**異なる実験**として管理する。

### ARC3

1. 2026-10-22頃の提出ID 57527856、Notebook arc3-hds-hold-baseline v5の公式結果を確定する。placeholder Parquet score=1は記録のみに留める。
2. 公式23.86のNotebook実体と0.03版のソースを、別々の版として取得・ハッシュ化する。画面の題名だけで同一性を決めない。
3. 183レベルのHDS記憶索引、成功軌跡、公開ゲームの進捗記録を、現行提出agentのロード／作用経路と照合する。
4. Kaggle履歴へ接続できなければ、ユーザーへ**不足する具体物**（Notebookファイル名、version、出力SHA等）だけ報告。別提出の成績を捏造しない。

### P0/P1の成果物

- 現行正本／歴史正本一覧（SHA・日時・相互関係）。
- 各既知スコアとNotebook／提出ID／コードの対応表。未観測欄を保持する。
- 未解決の再現条件一覧、次に確認する最短手段。

## 3．P2／P3：再現試験を先に成立させる

### P2：歴史的局所成果

1. 当時のデータ集合、学習前状態、ソルバー版、採用ルール、評価器をセットで凍結する。
2. 当時と同条件で実行し、結果／課題単位の正解数／保留／時間／副作用を比較する。
3. 一致なら再現PASS。不一致なら最初に分岐した観測、候補、Gate、出力を特定する。
4. 不一致原因が未確定なら「再現FAIL」、必要物がなく測れないなら「復元不能・未観測」。どちらも成功扱いしない。

### P3：新しい現行基準線

1. 公開入力の固定サンプルを選び、入力・評価器・記憶初期状態・seed・予算を保存する。
2. 同一条件で最低2回実行する。結果が一致しなければ非決定要因を同定し、事前に定めた複数回の再試験と許容範囲で判断する。
3. 同一入力の結果をローカルと提出用OFFLINE環境で比較する。
4. ARC2は解答格子・HDS採否・機構候補とエラー、ARC3は作用列・観測遷移・終了状態・レベル・作用数を比較する。
5. 結果と構成をSHAで凍結し、次のP4変更前基準にする。

**成績の記録種別**：学習対象・既知課題の再実行、履歴評価セット、調整未使用セット、公式hidden本番、を別ラベルにする。公開評価を過去に解析済みなら「初見性能」と書かない。

## 4．P4：最小改修順序

### ARC2（優先順）

1. 道具/ARC2Kaggle提出bundle.py と 接続/ARC2/HDS接続.py の読み込み資産を照合し、事前記憶の欠落・使用ゼロを実測で検出する。
2. 当該入力で元の学習機械がどの候補を生成したかを記録し、機構ごとに「未学習／候補なし／Gate保留／採用候補／候補競合」を分ける。
3. 有効候補が存在するのに別の機構の保留で全体がNoneになる経路を解消する。候補の根拠は保持する。
4. 接続/ARC2/Kaggle提出.py の二候補処理を一般的な候補選択へ更新し、入力コピー・同一候補のケースを計量する。正当性のない候補は正答扱いしない。
5. 公開サンプルから課題別の予測・正解・エラーを集め、どの変更が実際の正解増に寄与したか検証する。

### ARC3（優先順）

1. 23.86版を再取得できるなら元の制御ループ・記憶・行動方針を独立基線として保存する。
2. 道具/ARC3提出物構築.py と 接続/ARC3提出agent.py の記憶ロード・RESET後制御・MAX_ACTIONS・停止条件を照合する。
3. 初回観測後も合法なPROBE／EXECUTEを選び、環境状態→推論→次の作用へ戻るループを修復する。
4. 公開ゲームで少なくとも一つ以上の状態進行を実演し、進行条件、操作数、停止理由、得点計算を残す。
5. HDS既知軌跡を固定操作列の答え表に使わず、機構推定と一般化方策の入力として利用する。

一度に複数機構を書き換えて原因を失うことを避ける。原則「一つの失敗署名→一つの変更→targeted test→同条件local eval→回帰」。必要な大規模再構築は、その理由と保持条件が証明された場合に限る。

## 5．P5：形式合格と能力合格の独立検査

### ARC2能力検査

- テストで少なくとも「候補あり」「候補競合」「解決不能」「入力コピー」「二候補が異なる」を区別して再現する。
- 公開で正解が判明する格子の**本当に正しい予測数**を計測する。正答数0のまま候補数だけ増やしても改善PASSにしない。
- 課題を跨いだ一般化を、固定した未調整群または厳密に露出状況を注記した評価群で検証する。
- 障害時にも提出形式は壊さないが、形式正常を能力正常と混ぜない。

### ARC3能力検査

- RESET／停止が正常に動く試験だけでなく、公開ゲームで複数の合法アクションが出て、観測が更新され、レベル進捗に結び付く試験を必須とする。
- HDS判断HOLDであっても適法な追加観測／PROBE／別方策が可能なら継続する。盲目的な乱数連打や無限ループを認めない。
- 作用効率、クリアレベル数、ゲーム成功、得点をそれぞれ計測する。
- 学習機械の記憶を外した対照実験と比較し、関連する能力変化を監査する。

### P5受入制限

既存の「0動作で終了するテスト」「合法JSONを書けるテスト」は残してよいが、**これだけで総合PASSを宣言することは禁止**。能力検証が未成立ならP7の公式枠は消費しない。

## 6．P6／P7：公式採点までの接続

1. P5合格した実装・記憶の同じSHAを提出物に梱包する。
2. manifestのinclude／exclude一覧を検査する。必要な事前記憶を除外したまま「接続済み」と報告してはならない。
3. Kaggleの現行提出契約と制限、Notebookの依存、Internet OFF、CPU/GPU、action予算、実行時間、資格・当日枠を確認する。
4. 公開可能な同一入力でローカル実行と提出環境の出力／作用経路が一致するか確認する。
5. その日に最も根拠の強い候補だけを、利用可能な公式枠で採点する。改善の根拠なしに0点版を繰り返し提出しない。
6. 公式statusがPENDINGなら提出IDを保持し、次回の同一提出をしない。その間はP8の調査・局所実験を続ける。
7. 確定scoreとNotebook version、bundle SHA、Git SHA、変更理由を台帳へ書く。スコア改善・悪化は**同じ公式指標**で評価する。

## 7．P8：スコア駆動の継続作業

1サイクルで必ず残す項目：

| 項目 | 具体例 |
| --- | --- |
| 変更前 | Git SHA、公式／局所score、HOLD・正答・作用数 |
| 仮説 | 入力コピーが正答を阻害／RESET後に動作が止まる、など |
| 改修 | 影響ファイル、消した失敗署名、保持した境界 |
| 反証試験 | 対象ケース、Ablation、戻り検査 |
| 結果 | 同一集団の前後差分、公式提出IDと確定score（あれば） |
| 判定 | ACCEPT／REJECT／RETRY／UNOBSERVED |
| 次工程 | 再試験、追加観測、次の仮説、提出可能日 |

局所改善と公式得点が食い違う場合は、データ集団差、記憶・runtime差、選択・HOLD差、評価式差に分解して監査する。単に「汎化不足」で説明を終わらせない。原因が不明なら不明のまま適切な次実験を組む。

新しい仮説を追加するだけのコミットや、再計測しない大規模リファクタを成果に数えない。性能が悪化した案は実験履歴を残して不採用とし、動作正本へ混入させない。

## 8．進捗報告の固定形式

リポジトリごとに、Codexは各作業単位の末尾で次を日本語で短く報告する。

1. **目的／対象**：今回どの得点阻害要因を扱ったか。
2. **元の観測**：以前の条件・結果・SHAと確信できる範囲。
3. **操作**：何を保持し何を変更したか。
4. **再現試験**：同一条件で再現したか／どの地点で分岐したか。
5. **能力結果**：ARC2正答数、ARC3クリア・作用・局所得点。
6. **公式結果**：提出ID・版・スコア。未提出・PENDINGならそのまま表示。
7. **失敗署名／次工程**：既存成果のどこが再現できないか、何が必要か。

報告だけで作業継続を止めない。ただし継続可能な実行基盤がない場合、次作業の指示・状態・再開条件を残し、バックグラウンド運転を偽装しない。

## 9．最終検収

最終納品は「ソフトが動いた」ではなく、**各リポジトリの得点版を特定し、その版の実行条件・記憶・出力・正規スコアを追跡でき、改善案を同条件で再評価できる状態**。

最終成績はKaggleが公式に評価した値のみ。未観測のhidden性能や未実行の優勝可能性を完了として報告しない。
