3. **異常終了後の再提出に日付待ちはない**。実際のKaggle残枠と送信可否を確認し、送れるなら修正後に同日再送する。正常採点済みの枠とは区別。

5. 旧アーカイブ再現や形式テストは目的の**従属工程**。目的＝未知grid正解→学習の因果実証→公式得点最大化。

## P3（最大優先度、10/29～）本当に得点を増やす生成器・2試行

### P3-a：現行誤答を分類（最初の1–2時間）

公開の未見holdoutで各格子を`candidate_missing / candidate_wrong / correct_candidate_discarded / duplicate_attempts / fallback / timeout / data_error`に帰属。特に**正しい候補が作れなかったのか、作ったが選ばれなかったのか**を分ける。72候補の「追加的な正解0」は候補生成側か選抜側かを特定。

### P3-b：候補生成を拡張（最初の半日で実得点を確認）

- 旧HDS Family群を捨てず、**格子構造・物体・関係・合成演算を共有する汎用プログラム探索**へ接続。手動100個の関数増設ではなく、演算子の少数合成・train制約フィルタ・出力多様性のエンジンを実装。
- 複数train例を用いたパラメータ推定・leave-one-out・色役割置換・部分問題分解を入れる。組合せ爆発をbeam/枝刈り/段階予算で制御。
- **外部強力エンジンの候補化**：競技で使える公開OSS/モデル（必要ならGPU学習済み重み・test-time training）を**候補表**として比較。必要資産の無ネット搭載、ライセンス、GPU割当、12h内、実際の`pass@2`を受入試験。得点が強いものを早めに導入し、HDS側で採否・配分する。
- 最初に比較すべき具体例は**NVARC 2025公開ソルバー**（当時公開27.64%の実績）、**ARChitects公開解法**、2026の実行可能な強い公開DSL/TTT/公開重み。方式・モデル・学習重み・オフライン実行環境を区別して監査し、**モデル名だけで点数を引き継がない**。採用は同一公開holdoutに対する正答の増分と、Kaggleリソース内完走が条件。
- **順位と2欄**：スコア1位だけでなく、別の解法が拾える格子を2欄目へ。`unique_attempt2_hits`を必ず出力。偶然違うだけのランダム案は証拠なしなら低順位。

**継続採否**：一つの変更バッチにつき固定holdout上の`before/after`を算出。候補は増えたがpass@2増分ゼロなら「未改善」とし、原因帰属と次の仮説を更新。正答増・推論時間減・完走性向上のどれか実証した版を優先。

### P3-c：CPU/GPUを合理的に選ぶ

1. 本番で**GPU種・使用可否・残時間・メモリ・実際の読み込み**を確認。L4x4が表記上存在しても本人の利用可能性は別。
2. CPU版は正常採点の保険。GPU版は**得点/時間/メモリ**でCPU版を超えたとき採用。最強公開ソルバーでも再現不能なら捨てる。
3. タスクへの予算は一律固定せず、初回候補で解けた可能性・複数独立候補・残時間で再配分する。最終的に全件に合法outputがあることを保証。

**G3通過**：既存版に対し固定holdoutの**実正答格子数/総数・pass@2・2案独自寄与**が改善し、再現性と実時間が成立。

## P4（10/30～）HDSの成立実験と誤用境界の是正

1. 候補生成器を固定し、`A: HDS無 / B: HDS採否有・記憶無 / C: 初期記憶有・更新無 / D: HDS更新有`の4条件を同一入力/seed/時間枠で実行。
2. HDSが何を見たか（公開trainと汎用記憶）、何を保留したか、何を次の計算指示に変えたか、どの規則が新しいtest候補へ影響したかを追跡。
3. **HOLD≠行動禁止**：原理上は不確定を保持し、コンペでは明示的リスクで暫定解答を出す。候補生成器の独自格子を「HDSが証明」と偽装しない。
4. 記憶更新前後の実状態・採用規則・未見`pass@2`差を記録。性能変化がなければ学習効果を主張しない。悪化すればrollback。

**G4通過**：学習・非学習の帰属が再現可能。効果0の場合でも評価自体は完了だが、**「学習成立の実証」は未達**として改修を続行。

## P5（毎日、G1後も継続）公式スコア強化ループ

1. 出せる日は事前に`submissions history / current limits / best scored`を確認。
2. 未見holdoutで改善した版を優先してパッケージ化。新Notebook版＋hash＋必要な外部assetsを固定。scoring rerunを確実に完走する状態で提出。
3. `PENDING/RUNNING`ならpollし、開発は止めない。`ERROR`または`COMPLETE+errorDetails+score=null`なら**「未採点、成功0」**として即調査・修正・枠再照会・**同日リトライ**。次に移るための日付上限を人工的に設けない。
4. **正常数値score**（`0.00`を含む）なら`SCORED_ACCEPTED`として保存し、前回の公式ベストとの差を計算。次回の正常な提出枠はKaggleの現在の規則・残枠に従う。
5. スコア悪化版は因果を解析し、以前の高得点版を失わない。**最終2提出選択は、誤実装やスコアリング未成立版に使わない**。

**得点進捗の見える化**：公式スコア、公開評価`pass@2`、固定holdout`pass@2`、fallback/HOLD、2案寄与、CPU/GPU費用、残りの本番日数だけを日次の主要欄にする。通常heartbeatで進捗を代替しない。

## 実行コマンドの原則（現行CLIと照合）

以下は既存repoで確認された起点であり、**必ず実行前に`--help`・現行モジュールへ照合する**。`python -m uv`のような混在は避け、`uv`が存在すれば`uv run --locked python ...`、それ以外は実環境のPythonを使う。

```bash
git status --short
git rev-parse HEAD
uv run --locked python -m 接続.Kaggle操作 接続確認
```

次に、現行実装の説明に合わせてbuild/stage-upload/send/status/output/submitの順を実行。古いv6の具体コマンド列は検査対象であって命令の絶対値ではない。CLIにsubmissions limit取得コマンドが無ければ、**公式Kaggle APIの許可された読み取り経路**またはKaggle提出画面で枠の現況を確認し、追加実装の採否を決める。
