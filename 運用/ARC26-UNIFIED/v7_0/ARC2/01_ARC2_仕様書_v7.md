## 1. 契約：目的・成功・非成功

1. **最終目的**は競技での勝利と高い公式得点。85%は追加賞ラインであり、首位条件そのものではない。低得点を記録することは途中観測であって目的達成ではない。
2. **学習機械の成立**は、同一系で経験・更新により将来の仮説、候補、採否、停止または出力が変わること、その因果と未知問題への効果を実測すること。記憶ファイルの搭載、ログの増加、版番号変更ではない。
3. **実解答**は公開train入出力から汎用規則を推定し、test inputへ適用した出力格子。`HOLD`、inputコピー、無根拠な2欄複製は得点と区別する。
4. **公式成功**は`submission_id + notebook/version + source hash + official terminal status + 数値score`が一致し、エラーがなく公式に採点されたこと。`COMPLETE`という文字だけでは成功ではない。**0.00も数値が確定していれば採点成立**（低得点の正式提出）である。
5. 原点は既存資産の再使用。破綻した機構を漫然と上書きせず、分離、原因特定、復元・置換の採否を実測で決める。

**禁止する成果のすり替え**：形式PASS、全欄埋め、テスト件数、実行ログ件数、HDS呼出回数、採点不能なNotebook、旧版の高得点記録を、現行の正解率や学習効果として報告すること。

## 4. 必須アーキテクチャ：候補を生み、選び、結果から更新する

**ARC2入力→HDS観測・問題表現→複数の汎用仮説生成器→train制約検証→test出力候補集合→HDSによる採否・資源配分→異なる最大2試行→Kaggle出力→結果帰属・学習**。

機構を下記の契約で分割する。クラス名・言語を固定しないが、ログ上の境界は分離する。

### 4.1 ARC2観測／正規化

- 背景色候補、連結物体（4/8近傍）、色集合、面積、外接矩形、回転・反射同値、反復、周期、軸対称、線・端点、内部穴、隣接・包含・整列、入出力サイズ関係を**入力と公開trainだけ**から抽出。
- オブジェクト単位と格子全体を同時に保持。色の**数字そのもの**と「背景・マーカー・対象色」の**役割**を分ける。複数train間の対応を制約として記録。
- 観測不足・曖昧性・矛盾をそのまま記録。外部から取れない隠しtest outputの観測を必要条件とする仮説は、**実行可能な推論候補としては使えない**。

### 4.2 汎用候補生成：表現力を優先

候補生成は`生成器ID / 出典・バージョン / 汎用プログラムまたはモデル / train整合 / test格子 / 費用 / 失敗理由`を返す。次を**再利用可能な演算と合成**で実装・復元する。

1. 格子幾何：D4、平行移動、切出し、余白、サイズ変換、拡縮、繰返し、マスク、合成、重ね合わせ。
2. 物体：抽出、選別、ソート、色置換、構造コピー、移動、整列、鏡映、回転、連結・分離、カウント、補完。
3. 関係：最小・最大・同形、交差、包含、接触、方向、対応、パネル間比較、周期・境界条件、局所→全体適用。
4. 複合規則：少数演算の文法的組合せ、パラメータ推定、部分問題分解、条件分岐、構造化プログラム合成。特定のtask専用if文は不可。
5. **競技力を引き上げる外部実装の採用候補**：競技規則に適合する公開・再現可能なアルゴリズム、学習済みモデル、test-time adaptationを、ライセンスと実行資源を監査したうえで比較する。使えるGPU（L4x4等）は現場で実際に確認。不可ならCPU経路へ戻る。

探索順は**簡単な仮説から深い合成へ**。train全例を再現できる候補のみ有力視し、内部的にはtrain失敗仮説も反例として保存。`leave-one-train-pair-out`はtrain例が2件以上の場合に実施し、過学習検出へ使用。train1例の場合はLOO不能として記録し、汎用事前仮説・複雑度・候補多様性で補う。探索がゼロ候補なら、外部生成器と低順位探索を諦めず段階的に呼ぶ。

### 4.3 HDSラーニングマシンの責任を失わない

- 既存`HDS/学習系統/v0.4.2`と`記憶/事前記憶/v0.4`を第一資産とする。HDS Runtimeの判断は、目的・価値・リスク、候補集合、採否、SUSPEND、状態分離、Failure Signature、記憶更新、次の観測・計算要求へ具体的に反映。
- **原理上のHOLDと提出用の行動選択は別状態**。HDSが「この格子を真と承認しない」場合でも、コンペの限られた2試行には、出典・確信水準・リスクを明記した暫定候補を採用できる。**HDS承認と称してはいけない**。この判断はHDSの目的と損失構造に基づく、公開された暫定行動Gateで承認を記録。
- 反対に、矛盾する候補一つがHOLDを返しただけで、他候補の独立したtrain整合やtest出力まで破棄しない。各候補の検証状態を保持する。
- 既存事前記憶は「公開train群から得た一般的規則・失敗署名・探索優先度」として利用する。評価正解を埋め込む索引・task ID→grid表は使用不可。読み込んだだけでなく**検索・適用・採否を変えたトレース**を残す。
- Kernel原理をARC固有の失敗で安易に改変しない。まず`Domain Adapter`と`Runtime`の境界を修正し、Kernel改変は仕様で要求される別途の強い根拠・承認がある場合だけ。

### 4.4 候補ランキングと2試行の実利

候補は出力格子で重複排除。**先にhard constraints**（格子合法、train完全再現、実行可能、ライセンス、時間）を適用し、次に`train汎化/LOO`, `規則の短さ・適用の一貫性`, `他生成器からの独立支持`, `保留・衝突リスク`, `計算費用`を目的別に評価する。**票数のみ**を順位の絶対基準にしない。下位候補の正解機会が消える反例を保存する。

- `attempt_1`は最も整合的な高順位候補。`attempt_2`は**正答を独立に拾う見込みがある別格子**。候補が一つだけの場合の形式上の重複は「試行2の寄与0」と記録。
- 実力の指標：`pass@1`,`pass@2`,`unique_attempt2_hits`,`distinct_attempt_rate`,`candidate_coverage`,`fallback_copy`,`HOLD`,`time_out`,`wall`。最適化対象は`pass@2`の真の増分。
- 同じ候補でも、色役割・構造帰納による予測と偶然の入力コピーを混同しない。input＝output変換がtrainで成立した場合だけ、コピーを真正候補と認定。

### 4.5 処理予算と完走性

- 競技のNotebook制限：CPU/GPUとも最大12時間、実行中のインターネット不可、出力ファイル名`submission.json`。アクセラレータ・必要データセット・GPU残時間は本番環境で確認して確定する。**GPU未確認を採用済み前提にしない**。
- **内部ウォッチドッグ**で総予算を12時間より十分短く管理し（初期設定例：10時間30分以内）、終了前に少なくとも1時間以上を書出し・完了へ残す。task単位のハード制限、失敗隔離、スケジューラの強制停止、OOM防止、依存読込の固定を用意。
- 候補生成を**容易→中程度→困難**の段階に配分し、残時間・既存候補数・期待限界利得により演算量を変える。259出力の「処理済」を保証してから難問へ追加計算を配分。CPU版は迅速な採点確認用、GPU等の強力版は高得点候補。両方に同じI/O契約を使う。
- ノートブックの「一度だけの私的run成功」はスコアリング時再実行の完走保証ではない。公式scoring kernelのログとエラーを別途確認する。
- 合法格子を埋める最終フォーマットfallbackは残してよいが、**不得意の証拠として別管理**。失敗が別のtaskを巻き込まないことを確認する。

## 5. 旧120/167成果の扱い：復元するが、ここで止まらない

旧アーカイブ`ARC2-main-delta-120-167-evidence224.tar.xz`を、コード/環境/入力版/採点器/ログと分離。hashが整合したという事実は**結果再現ではない**。実行前に文字コード（Windows cp932問題）、依存、CPU制限、評価正解の参照境界を点検し、最小サンプル→旧版全件の**同一条件再現**を試みる。

復元結果は①再現・漏洩なし：機構移植、②部分再現：新旧の差分抽出、③非再現・ルール上不採用：根拠を残して打切り、と分類。**復元作業には有限の時間枠を設ける**。旧版の数字を追うために公式得点を確定させる作業や新規候補生成を停止してはならない。変更は新旧A/Bで`pass@2`が増えたものだけを性能成果として採用する。

## 6. 学習の実証：HDSの因果と実用を分けず測る

固定した未見holdoutに対して、同一候補生成器・同一計算・同一seed・同一train/testで以下を比較。

| 条件 | HDS判断 | 事前記憶・適応 | 何を区別するか |
|---|---|---|---|
| A | 無効/固定ルール | 無効 | 生成器だけの能力 |
| B | 有効 | 初期記憶固定 | HDSの候補選択・予算配分寄与 |
| C | 有効 | 汎用事前記憶有効・更新停止 | 事前知識の寄与 |
| D | 有効 | 更新可能 | 継続的学習の寄与 |

**A→B、B→C、C→Dそれぞれの`pass@2`差分**、選ばれた実出力、状態の前後hash、採否記録、使用した観測と反例、機構別失敗原因を保存。Dに改善がなくても「学習効果未実証」と正確に報告する。更新される実体は仮説優先度/探索手続き/失敗署名/汎用記憶等で、**単なる追記ログではない**。新しい判断が反例で悪化すれば取り消し・降格できる。必要なら公開training内で複数のholdout seedを設け、固定評価セットの都合のよい結果だけを採らない。

## 7. 公式提出の状態機械：エラーは受理扱いにしない

**競技ルール**は原則「1日最大1 Submission」「最終選択最大2件」。ただし**エラー終了は得点成立と同一でない**。事実としてARC3側では多数のERROR後に同日成功した報告もあるが、ARC2の失敗時枠消費を一律保証する公式文言は未確認。従って**Kaggleの実際の受理・残枠**を毎回読んで運用する。

| 実際の状態 | 判定 | Codexの即時動作 |
|---|---|---|
| 未提出・パッケージ不正・送信HTTPエラー | `NOT_SUBMITTED` | 問題修正、Notebook版・フォーマットを再検証、再送。枠残を照会 |
| `PENDING/RUNNING` | `IN_PROGRESS` | 状態追跡。採点完了と誤認しない。合法なら並行して開発 |
| `ERROR`、timeout、kernel障害 | `TERMINAL_ERROR_NOT_SCORED` | 正確なログ採取→原因別修正→残枠照会→**枠がある限り同日中に何度でも再提出** |
| `COMPLETE`でも`errorDetails`有りかつ数値scoreなし | `TERMINAL_ERROR_NOT_SCORED` | **成功・採点済みと絶対に扱わない**。ログ、残枠、修正、即時再試行 |
| `COMPLETE`等かつエラーなし・数値score有り（`0.00`を含む） | `SCORED_ACCEPTED` | 採点済みとして固定。枠消費・次に提出可能な時刻を公式照会し、次期提出を計画 |
| API不整合・状態不明 | `UNVERIFIED` | 成否も枠消費も推測しない。Kaggle履歴/制限/出力を照合 |

**再提出ループの絶対条件**：エラーのまま「本日分は使った」と決めつけて翌日まで止まらない。逆に、エラーなら必ず無制限と推測しない。`submission limits`・履歴・実APIの応答を照会し、送信可能なら同日中でも**根治または妥当な切分けを伴う再試行を継続**。再送数の人工的な固定上限は置かず、APIの制限、残計算枠、期限、実際の解消見込みを制御条件とする。正常に採点された`0.00`をエラーと偽って枠を迂回しない。他アカウント等による制限迂回は不可。

`score=null`だけで即断せず、進行中と終端エラーを区別。返却`COMPLETE`の意味とKaggle上の競技提出の採点状態を分離する。Notebookコミット成功・Private run完走・`submission.json`有りは`SCORED_ACCEPTED`の代替にならない。

## 8. 受入検査・観測契約

**各実験の必須証拠**：`run_id, UTC/JST日時, git SHA, 依存lock/hash, データ版/hash, 予測器/記憶版, train/eval/testの厳密分離, cpu/gpu, 実行予算, 観測母数, pass@1/pass@2（採点可能時）, 追加2試行寄与, fallback, HOLD, timeouts, wall, 修正箇所, A/B差分`。

**各公式提出の必須証拠**：`kernel slug/version, notebook commit/build hash, submission_id, Kaggle実ステータス, errorDetails, error category, official publicScore（数値またはnull）, submission-limit照会結果, 再提出判断, 公式スコアがあるなら前回との差`。

検査を3層とする：

1. **機械検査**：公式sampleのI/Oと完全一致、全task ID・test順序・attempt形式、合法1–30×1–30の0–9整数、`submission.json`出力、エラー隔離、12h以内。
2. **性能検査**：同一データ・制限・評価器で`before→after`。整数正解数と分母、未処理含めた分類、改善箇所と反証を示す。公開training未見holdoutを第一判断に使用し、evaluationへの反復適合を監視。
3. **公式検査**：上記状態機械で終端の数値スコアを検証。**エラーなら根拠を確定し、残枠があれば即時リトライ**。公式得点向上は実際のKaggle値でのみ主張する。

## 9. 非交渉条件と競争戦略

- 最初の実利は**少なくとも1件の正常採点された公式提出**（新しいNotebook実装の完走を確認）。その後の目的はスコアの伸び。初回`0.00`は達成ではなく参照点。
- 大幅な伸びは **(a)合法な高性能公開ソルバー・モデルの比較と統合、(b)汎用プログラム合成探索、(c)HDSによる候補選択・更新、(d)2試行の相補性、(e)計算資源配分** から得る。既存100 familyの微調整を最上位戦略にしない。
- **具体的な比較候補**：2025 ARC2のNVARC（公開コード、当時Kaggle公開得点27.64%）、ARChitectsの公開方式、2026の合法な公開DSL/モデル/TTT実装。**過去の27%級を再現しても2026首位88%級には届かない**。各ソルバーの候補出力集合の相補性と現行HDSによる増分を測り、実測効果のない丸写しは採用しない。
- 外部資産は規則上の公開性・公平性・利用許諾・再現可能性、出力物の権利を審査。ネット非接続のKaggle本番に同梱/データセット追加して完走可能なものに限定。
- **賞の資格と非開示原則の衝突を事前解決**：ARC2公式は入賞資格として**提出コードおよび使用方法のオープンソース化**を要求する。HDSの非公開中核や実装方法を公開してはならないというOwner方針を自動的に上書きしない。公開義務を満たせる**公開用Domain Adapter/ソルバー/既公開資産**で出場可能か法令・規則上の適合性を検証。**秘密中核の公開が必須となる構成はOwner承認なしに採用・公開・優勝資格適合と主張しない**。満たせない場合は「公式スコア獲得」と「賞の受給資格」を分離してOwnerに判断を仰ぐ。
