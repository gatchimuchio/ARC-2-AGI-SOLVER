## 0. Ownerの目的・失敗防止（省略不可）

Ownerの目的は**ARC Prize 2026のARC-AGI-2とARC-AGI-3で勝つこと**。既存のLearning Machine、公開サンプル、全解析・既存攻略資産がある。要求する仕事は：

1. **最優先で公式の数値スコアを取得**し、出所・採点対象・コード版を明らかにする。
2. **その後**、既存の学習・推論・攻略資産を実際に採点されるsolver/agentへ接続し、得られた公式スコアと失敗署名を根拠に能力を改良する。
3. 以後、各大会の提出可能な日に**1日原則1回ずつ**「改善→局所試験→本提出→公式スコア取得」を継続し、締切時に最良版を選択する。

**禁止する終わり方**：テストPASSのみで完了、Notebook COMPLETEのみで完了、submission.json/parquet生成のみで完了、Kaggle受付PENDINGのみで完了、公式スコアなしの最適化開始、HOLD-only agentの正式攻略扱い、途中工程でOwnerの追加指示待ち、単なる報告を作業の終点とすること。

初回スコアが**0**でもよい。**NULL・空欄・PENDINGを0へ読み替えることは禁止。**

## 1. 着手前の必読と保護規則

1. まず両リポの最新`main`を安全に取得し、対象・head SHA・未反映差分・有効な`AGENTS.md`・`制御/現在状態.json`・最新3点セット・実装・テスト・Kaggle実績を読む。既存の作業差分を消さず保護する。
2. 指示の優先順位はOwner原文→各repo AGENTS→保護現在状態→現コード・テスト・実測→今回3文書→旧指示。規範への実際の衝突があれば、衝突する文言と対象を記録する。
3. **`AGENTS.md`、`制御/現在状態.json`をOwnerの明示許可なしに編集・削除しない。** `自動遷移:false`をtrueへ書き換えて誤魔化さない。新しい運転状態は保護ファイル外の新規台帳で保持する。
4. 既存HDS正本`HDS/学習系統/v0.4.2`、`入力/`、`記憶/事前記憶/v0.4`、現行の成功・失敗証拠・既知成功提出物を保持し、全置換より動作接続を優先する。
5. Gitはmain正本、履歴破壊・force pushなし。外部提出は競技名・残枠・Kaggle本人アカウント・利用権限を確認。認証情報をリポや成果物に保存しない。

## 3. 公式数値が出たら、既存資産を本番の実動作へ【G3】

### ARC2の手順

1. 既存`接続/ARC2/HDS接続.py`と`接続/ARC2/Kaggle提出.py`、`検証/ARC2評価.py`、HDS正本を読み、**どの段で259格子中258格子がHOLDになったか**を機構／採用条件／教師例／timeout／依存関係に分けて再現・計測する。
2. 計測上の事実と原因仮説を分ける。「正答が出ない」をフォールバックの作成で解消した扱いにしない。
3. ARC2用HDS推論の入出力を修理し、各タスクの公開train入出力とtest入力だけを利用して一般化可能な候補格子を出せるようにする。局所ローカル評価は推論器へtest正解を渡さず実行。
4. 正当な別候補が成立する場合は`attempt_2`にも反映。未成立なら形式上2候補を出せるが、複製を能力向上に数えない。
5. 実際のKaggle challengesから課題数・test数・順序を動的に読み、全数入力／2候補形式／型／寸法／色を試験。120課題ローカル試験は本番スコアではない。
6. previous/current/deltaを同じローカル条件で測り、既存達成分の回帰と新規非HOLD・正答の増分を別々に報告する。

### ARC3の手順

1. `接続/ARC3提出agent.py`、`接続/共通観測経路.py`、`接続/ARC3境界.py`、`道具/ARC3提出物構築.py`を読み、**なぜ現行agentが合法行動を返さないか**をコードと実行で確定させる。
2. HDSの`実行許可:False`を無理にtrueへ変換しない。別の**ゲームプレイ用行動制御層**を設け、合法作用集合・探索の採否・リスク・予算・中止条件を記録してGameActionを返す。
3. 公式SDK契約に適合した`is_done`／`choose_action`を構成し、`MAX_ACTIONS=1`に由来するHOLD-only即終了を解消。行動の都度、公開観測→HDS状態・学習→行動→作用結果→更新へ戻す。SDKのenv.step相当は二重起動しない。
4. `記憶/事前記憶/v0.4`および既存の解析・学習状態を、出所・ライセンス・公開承認・公式規約上許容される部分だけ正規パッケージへ供給し、**新規プロセスで読込成功**を確認。GitHub公開が許可されない原本は公開しない。
5. 公式Starterを使う独立したローカルセッションで、複数の非RESET合法作用、再観測、エピソードの終了条件、少なくとも代表複数ゲームの実行ログを確認。公開サンプルの既存14レベル到達は**現行agentの能力とみなさず**再測定。
6. Kaggle Phase Aの`submission.parquet`ダミーやNotebook COMPLETEを最終得点としない。公式Competition Rerunで作動する版を提出し、公式scoreを確認する。

**G3のFAIL例**：ARC2は全問入力コピーなのに形式テストPASS、ARC3は0作用なのに11テストPASS、事前記憶未同梱なのに「学習反映済み」、いずれも不合格として扱う。

## 4. 初回スコア後の日次運転【追加承認待ち禁止】

1. 各大会で直近の**公式score原値**を確認し、観測できたHOLD・失敗・低達成の分布から優先度の高い**一つの原因仮説**を選ぶ。
2. その仮説を試す最小のコード変更を行い、targeted test→同条件local evaluation→回帰検査→差分監査を実施。スコア改善を見込めない変更や全面refactorを本番の最良版に混ぜない。
3. 当日の提出枠・UTC日付・未完了提出・Notebook環境・残資源・大会ルールを照会し、最良の適格版を各大会**最大1件**、正規の経路で提出する。ARC3はPhase B Competition Rerunを本提出とする。
4. 受付IDを保存し、同IDのstatusと公式scoreを完了まで監視。数値が出たらprevious/current/deltaを記録。悪化版を最良版と取り違えない。採点待ちを「改善済み」扱いしない。
5. 提出できない場合は原因・残枠・次の合法時刻・次の検査を記録。無駄な同一版重複提出で「毎日継続」を装わない。
6. 次の日は保存済みの**最新公式スコア・最良版・失敗署名・再開位置**から開始し、前日の文脈を記憶だけで補完しない。

大会の締切は原則2026-11-02 23:59 UTC（JST翌日08:59）、開始時と提出前に現行公式を照合する。両大会で最終選択できる最大2提出を確認し、最良実測と版を凍結する。

## 5. 継続実行の現物検査

- **Codexの会話継続や『これから監視する』という文章はスケジューラではない。** 実際に使えるWindowsタスクスケジューラ、認可済みCI、または同等の定期実行環境で、少なくとも「採点状態の照会→台帳保存→次回再開」を実動作させ、プロセス停止・再起動から復旧試験する。
- 自律的なコード改良までの無人運転を必要とする場合は、その処理を実際に実行できるCodex起動手段・認証・資源の有無を検証する。未実装なら**自動日次開発成立と宣言しない**。できる監視とできない開発を別記し、Ownerが判断すべき具体的権限だけ報告。
- 提出を開始する前に当日・大会別に`submitted_count`、`last_submission_id`、`pending`を確認し、再起動による二重送信を防ぐ。
- 2repoの証拠・運転台帳・再開状態は混ぜずに別管理。公開したくない生の実験記録は公開repoへ無断登録しない。
