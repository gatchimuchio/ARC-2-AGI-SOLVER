**基準：2026-10-29 JST／最終提出期限：2026-11-03 08:59 JST（11-02 23:59 UTC）**

## 工程原理

- **施工対象はLearning Machine**。既存資産や公開強モデルはこの機械の観測・生成・推論・記憶・実行を補助する部品。外部モデル単独提出による得点を最終成果に読み替えない。
- **工事の成果は正答数、公式スコア、学習因果効果**。テストPASS、ファイル生成、Notebook COMPLETE、分析資料、旧既知問題の正答数を代替しない。
- **今ある公式0.00の得点経路は基線として再利用**。すでに通っている公式送受信を何度も作り直さない。定期監視も既存成功経路を使う。
- **原因→最小または必要十分なコア改変→同条件評価→採否→次の原因**を途切れさせない。局所差分0なら別アーキテクチャ候補を試す。予定時間は目安であり、反証可能な結果で工程の優先順位を更新する。

## G1：Learning Machineの実推論閉路を稼働（初日・G0直後）

**課題**：既存`HDS/学習系統/v0.4.2`の呼出回数と実回答への寄与が一致していない。240課題/259格子で249 fallback、32 LOOの生成0という記録を起点にする。

1. 1課題の経路`公開train→観測→候補生成→教師照合→反例→修正→test候補→HDS採否→二試行`を、候補値を漏らさないログで追う。**最初の目標は機械が未知入力に対して根拠ある非コピー候補を出すこと**。
2. 課題ごとにHDSを生成し直す設計が一般記憶を消していないか確認。必要なら**学習系統の内部状態・永続化・適応・推論などの実装コアを変更**し、一般記憶を課題横断で再利用する。固定答え表は作らない。
3. まず公式サンプルの2～5課題とtrain内LOOで最小閉路を動かし、次に事前登録された開発/holdoutへ拡張。途中で非公開test出力の追加観測を要求する経路は、競技Actionから切り離す。
4. `HOLD`と暫定回答Gateを分離。HDSが不確定とした候補でも、教師整合を持つ別案なら二試行を合法に発行できるようにする。HDS真理承認を偽造しない。

**PASS**：少なくとも`候補根拠・HDS判断・実出力`が連結され、過去のfallbackに対して新しい合法候補を生成し、同一条件の未知出力採点が可能。**FAIL**：接続や状態更新だけで出力差がない。FAILなら生成器、表現、記憶境界を特定し、後続G2で改変する。

## G2：生成能力を増強し、実正答を純増（初日〜10/31）

### G2-A：既存機構とプログラム帰納

1. 既存familyの成功・失敗を`candidate_missing / train_conflict / correct_candidate_rejected / fallback / timeout`へ分類。多い原因から直す。
2. 物体・色役割・D4・クロップ・領域選別・反復・配置関係・複合演算を**trainから変数を推定する汎用プログラム**へ組み直す。train全例を再現し、LOO可能なら反例で候補を降格。
3. 学習機械自身が生成器・演算順・探索予算を選び、失敗署名に応じて次課題以降で選択を変える。外部から正解を教え込む固定task辞書は禁止。

### G2-B：強い公開生成部品の受入（G2-Aと並行、初回調査は最大2–4時間）

1. 既存v8で候補となったNVARC/TRM/Qwen系Kaggle公開Notebook（表示31.11）の**現存・依存・重み・ライセンス・推論時の入出力**を実際に確認。他者の数字を本チームの得点として扱わない。
2. 外部VARC候補には`checkpoint 216,495,359 bytes`の資産検査があるが、推論未実行・環境不備・evaluation解答混入リスクが残る。**アーカイブ丸ごとを推論環境へマウントしない**。ソース/重みを限定し、評価正解を物理隔離。固定100件中36件の既知ID重複から追加holdoutを作る。
3. 適合した候補の`予測格子・候補確信度・実行費用・失敗情報`を**Learning Machineへの生成部品インターフェース**として接続する。単独得点は比較基準、学習機械を通すscoreと因果差分は別計測。
4. 取得不能・ライセンス不適合・GPU不適合・隔離不能・12時間超過なら`REJECTED/NOT_READY`の理由を残し、別の合法なモデル／CPU帰納へ直ちに切替える。

**PASS**：同じ追加holdoutで`pass@2`のネット正答が増え、計算制限内で再現できる。**FAIL**：候補数や出力差だけ増えた、得点増分0、または汚染境界不明。FAIL版は得点改善としてmainへ積まない。

## G3：学習定義の実証（G1から計測開始、10/30〜11/01に集中）

| 条件 | 固定するもの | 変えるもの | 観測する因果 |
|---|---|---|---|
| A | 同一候補器・seed・入力・計算予算 | Learning Machine判断・記憶なし | 生成部品の素の実力 |
| B | 同上 | Learning Machineによる採否・探索あり、汎用記憶なし | 判断の効果 |
| C | 同上 | 汎用事前記憶あり、オンライン更新停止 | 記憶呼出の効果 |
| D | 同上 | 同じ初期記憶から更新有効 | 経験からの適応効果 |

1. 学習前後の`仮説、候補順位、採否、停止、追加計算、出力、state hash`を記録。値の変化だけでなく**後続入力に適用された変更**を追う。
2. 公開training内の複数課題を順次与え、学んだ一般的規則が別課題で使われるか確認。テスト解答は学習機械へ渡さず、隔離した採点器だけが予測後に読む。
3. `C`の照会で状態が変わるならsnapshotで固定条件を成立させる。`D`が悪化したら反例を使い規則の降格・失効を検証。
4. `A→B`、`B→C`、`C→D`を同条件の実数で比較。差0なら未実証と記すが、**なぜ差0かを次のコア修正原因として採用**する。

**PASS**：経験による更新が次の判断・出力を変え、未見holdoutの正答差で効果を評価できる。**FAIL**：ログ追加やメモリhash変化のみ。**理論の学習成立と競技得点は一つのLearning Machineの別の測定軸**であり、必ず併記する。

## G4：競技の公式採点・日次改善（G1以降、各合法提出機会）

1. 競技枠を確認し、**数値得点の改善見込みを持つLearning Machine版**を選ぶ。前回版の`source/asset SHA`、private実行、`submission.json`、形式・制限・学習機械依存関係を確認。
2. Notebookを送信、指定版の実行と出力を確認、合法な公式コンペ提出を行う。`submission_id`、`kernel/version`、`hash`、`errorDetails`、`numeric publicScore`を結合。
3. `PENDING`は重複送信せず追跡。終端ERROR／数値なしは原因修正→実際の残枠・再送可否照会→許可される場合のみ同日再試行。`0.00`は採点成功、成績失敗であり枠迂回はしない。
4. **公式得点が増えてもHDS学習効果の証明は別途必要**。外部部品だけの得点をLearning Machine得点と誤帰属しない。得点が増えない間もG2/G3を続ける。

既存の定期score監視は2026-10-29 07:03 JSTに履歴観測成功。監視の維持へ工数を吸い込まれず、生成・学習の実験を優先する。
