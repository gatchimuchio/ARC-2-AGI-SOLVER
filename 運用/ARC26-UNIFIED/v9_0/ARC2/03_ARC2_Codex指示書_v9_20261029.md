## 0. 命令の意味を取り違えるな

> **既存HDSラーニングマシンを学習・推論・意思決定の主体として、公式サンプル、既存リポジトリ、事前記憶、合法な外部モデルを教材・部品に用い、未知ARC2格子を正解する能力を学習で獲得・改良し、Kaggleの公式得点を伸ばして入賞を狙え。**  
> **この同一Learning Machineの経験→記憶→推論→適応→次の判断・実出力変化を、反証可能なA/B/C/Dで実証せよ。**

これは**独立した二製品（外部高得点solverと別のHDSデモ）を作る指示ではない**。性能の強い外部手法はLearning Machineの観測・候補生成・計算・検証の道具として接続する。外部solverだけを提出してHDSをimportしただけでは達成ではない。

**OwnerはLearning Machine実装コアの必要に応じた改変を明示的に許容している。** Adapterだけに修正を強制しない。原因が`推論.py`、`適応.py`、`系統.py`、`実行系.py`、`台帳.py`等の実装内部なら、その責任箇所を変更してよい。別承認を毎回求めない。変更と成果は同条件で検証し、効果0や回帰なら採用しない。

ただし、秘密HDS Native／神域原理・HDS理論正本、`AGENTS.md`、`制御/現在状態.json`、Ownerの権限・公開範囲は無断変更しない。理論を「改変可」と読み替えない。

## 2. 1サイクル目：学習機械が予測を作る閉路を復旧

1. 既存HDSの課題作成、観測、`候補機構を学習`、照会、判定、予測格子出力、`結果を候補へ`を一続きでトレース。最初の公開サンプル2～5課題で`候補がない／教師不整合／HOLD／fallback`を分ける。
2. 公式trainが1例しかない場合も、汎用的な構造・事前原理とプログラム生成で候補を試せるようにする。**他課題の正解を当該課題の証明にするな**。モデルが候補0のままなら、単なる閾値緩和ではなく演算・表現・探索機構を改変する。
3. HDSの認識保留と、コンペ上の暫定回答を分離。HDSが`HOLD`でも妥当性を明示した複数候補を比較し、制限内で二試行に配置する。未確定を「HDS確定」と書かない。
4. Learning Machineは、候補器を呼び、教師に合うかを検証し、反例で候補を更新し、探索予算を割り当てる**主体**。既存の候補器だけで完成出力を作り、HDSを後からimportする設計を採らない。
5. 適応した一般規則・優先度・失敗署名は**次の課題に継承**。課題固有のgrid、task ID/hash、評価正解、hidden情報は記憶へ入れない。ゲーム単位／課題単位のHDS新規生成で必要な一般記憶が消えるならコードを修正する。
6. 変更は担当する最小ファイルへ実装し、targeted test → 公式サンプル → 固定開発集合 → 追加holdout → 回帰の順に実行。分析だけで終了しない。

**最初の受入**：少なくとも、`同一HDS個体の経験前後で次課題の候補・採否・探索・出力のどれが変わったか`をログ上で追え、実際の出力格子が採点可能である。変化がない場合は`NOT_ESTABLISHED`と記録し、原因モジュールを改変して再実行。

## 3. 競技得点を生む部品を選び、Learning Machineへ結合

- **プログラム帰納**：D4／物体選別／色役割／包含・接触／クロップ／反復／局所→全体／パネル関係／条件付合成を、入力から推定可能な型付きプログラムとして実装。train全例の実行差分から反例を導き、候補を再生成。
- **合法な公開モデル**：候補として公開NVARC/TRM/Qwen系Notebook等を実確認。ライセンス、学習済み重み、入力依存、Kaggle L4x4可用、RAM、無ネット、12h、scoreの版を実測。モデルと解答ラベルの混入が疑われる資産は隔離・不採用。**汚染された強基線に学習機械の点数を仮託しない**。
- **部品の採否**：外部モデルが使える場合も`generate(train, test_input, budget) → candidates + evidence + cost`に相当する責任境界を設け、HDSが候補選択、反証、追加探索、記憶、二試行に実際に関与する。部品単独のscoreと、Learning Machine経由のscoreを同条件で比較する。
- **二試行**：第1候補と独立の第2候補が拾う正答差を記録。二欄重複は追加寄与0。単純なidentityコピーは最後の形式fallbackであり実解答能力として計上しない。
- **失敗時**：候補なし、推定誤り、HDS棄却、前処理不整合、LOO矛盾、タイムアウトなどを集計し、最大の得点損失源から次の改修を選ぶ。**有望でない微細familyを増殖しない**。

## 4. 学習定義を同じ本番対象で反証せよ

事前登録した公開training開発／追加holdoutで、**同一候補器・モデル・seed・計算予算・データ版**を用い、

- `A`：生成部品のみ（Learning Machine判断なし）
- `B`：Learning Machineの採否・探索あり、汎用記憶なし
- `C`：汎用記憶あり、オンライン更新停止
- `D`：同じ初期記憶でオンライン更新あり

を比較する。

採点器は別プロセスで予測後だけ正解を読み、推論runtimeにtest outputを入れない。既存100件の`VARC関連36件ID重複`は露出疑いなので、追加の事前登録・重複除外集合を使う。未見性が証明できない場合は`exposure_unknown`と書く。

必須測定：`candidate_count`、`selected_program/grid`、`HDS_action_reason`、`extra_search`、`memory_before/after_sha`、`next_task_decision_delta`、`pass@1`、`pass@2`、`unique_attempt2_hits`、`fallback`、`wall`。

**学習成立**の最小条件は、経験により未来の推論・採否・行動の一つ以上が実際に変化し、反例で更新または撤回できること。**競技に有用な学習**はさらに未知課題の正答増分で検証する。変化0なら`NOT_ESTABLISHED`、悪化なら不採用。`state hash`の変化だけを学習と宣言しない。

## 5. Notebook・公式提出は得点と版で閉じる

1. 本番NotebookはCPU/GPU最大12時間、Internet無効、`submission.json`の公式schema、2試行×test出力数、0–9整数・矩形・合法寸法、全task ID/順序と照合する。評価解答、credentials、秘密ログを同梱しない。
2. build→stage-upload→push→指定版のprivate run/出力検証→合法なCompetition Submit→数値score確認。各操作の現行CLI契約を`--help`で照合する。競技提出は`competition_submit_code`等の**正規版指定API**を使い、ローカルJSONの通常ファイル投稿と混同しない。
3. `submission_id`・`kernel slug/version`・`source/asset SHA`・`status`・`errorDetails`・`publicScore`・`quota`を紐付ける。`COMPLETE+0.00`は公式採点成立、成績不成立。`COMPLETE+null+errorDetails`は未採点、`PENDING`は追跡、`ERROR`は原因別に修理。
4. ERRORの後は**実際の残提出枠・送信可否**を確認し、許されるなら同日でも修正版を再提出。数値採点済みの枠をエラー扱いしたり、複数アカウントで枠を迂回したりしない。status不明では重複送信しない。
5. 既存`57745630=0.00`を得点出口の証拠として再利用し、**新しい正解能力がないまま採点枠を消費することを主工程にしない**。公式改善版の最終選択は最大2件、締切は2026-11-03 08:59 JST。

## 6. 実装の権限・Git・秘密保全

- 作業対象はARC2のみ。ARC3とPaper Trackを巻き込まない。外部資産は必要な部品として審査するが、目的外のAGI・ミニドラ系を復活させない。
- `AGENTS.md`、`制御/現在状態.json`、理論正本をOwner承認なしに書換えない。HDS Learning Machine**実装**は可変。変更は因果仮説・対象・回帰・得点差分を保存して、成立したものだけ採用する。
- `main`一本を基本に、既存未コミット変更・証拠・履歴を保存。強制push、history rewrite、不要なPR/branch、過去結果の消去は禁止。採用前の試作は隔離作業領域で管理する。
- 公開モデルの重み・ライセンス・データ露出・受賞公開義務を証拠で調べる。Ownerが保護する秘密HDS Native／運用ログ・Codex指示全文・failure signature詳細を勝手に提出・公開しない。
- 動作環境・GPU割当・Kaggle認証が阻害された場合、権限外に迂回せず、**実阻害点とOwnerの最小必要操作だけを報告**。それまで可能なソルバー・HDSの改修と局所検証は継続する。
